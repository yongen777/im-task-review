- 日期：2026-11-09
- 状态：**设计稿（未动代码）**。本文只描述「要做什么」与「为什么这么切」，不含实现。
- 应用：自建应用 `143e30e8-8323-4229-b2e2-ab77836dedbb`（OPS任务调度助手）

## 〇、先说结论：三件事是一件事的三个阶段

用户提出的三点，看起来是三个独立功能，实际是**同一条链路的三个环节**：

```
① 用户触发式任务  →  ② 任务收集好的数据统计  →  ③ 数据喂给知识库
   （入口）            （出口）                    （增值）
```

平台现在只有**中间那一段**：平台按周期主动推送 → 用户填 H5 → 数据落在 `submission.fields_json`。
两头都空着：入口没有（用户只能被动收提醒），出口没有（数据收上来了但没人看）。

**设计主张：一次把三段打通，用同一个数据模型**。理由是第②段（统计）的价值完全取决于第①段
「谁在什么范围内、什么时点、收了几份」的语义；如果①按「不分人不定期」的形态落地，
②的模板就必须能表达「按触发批次」而不是「按周期」——**先定①的数据模型，②才有地基**。

## 一、现状核实（本文所有结论的事实依据）

> 以下均为对当前生产代码的核实结果，不是推测。

### 1.1 用户发文本给机器人的链路**已经存在**

| 事实 | 位置 |
|---|---|
| 两通道共用同一业务入口（量子密信 + 企微） | `app/api/events.py:145` `handle_incoming_text(...)` |
| 企微通道解 XML 后调同一函数 | `app/api/wecom_callback.py:91` `if msg_type == "text"` |
| 已绑定用户发**非手机号**文本 → 机器人固定回复 | `app/api/events.py:215-224` |

### 1.2 用户给的那段话，**就是现在的 ack 文案**

`app/api/events.py:217-222` 现存文本，与用户描述逐字一致：

```
【OPS任务调度助手】
你好，消息已收到。我是任务调度助手，只负责按设定时间推送任务提醒、收集上报内容，
暂时看不懂聊天和其他文字指令，这里不需要你回复文字。
任务提醒会按时自动送达，届时按提醒里的链接或表单提交即可；业务问题请联系对应管理员。
```

**这是本设计最重要的落点**：第①项需求不是「新建一条通道」，
而是**把这段固定 ack 换成分支菜单** —— 同一段入口代码，从「无脑回同一句话」变成「识别意图 → 回菜单」。

### 1.3 现有的「指令」先例：申请补交

`app/api/events.py:186-213` 已有一个**文字指令**的实现先例：

```python
apply_text = (msg_text or "").strip().strip("【】[]　 ")
if apply_text == "申请补交":
    res = state.request_resubmit(bound_member["phone"], ...)
    # → 分 applied / already / window_expired / admin_disabled 四种结果，各自回不同文案
```

**可直接复用的四个模式**：① 文本归一化（去括号空格）② 指令 → 状态机 ③ 结果分支回文案 ④ 幂等保护。

### 1.4 现有模板模型的硬约束

| 约束 | 事实 | 对新需求的影响 |
|---|---|---|
| `kind` 枚举 | `("form", "image", "file", "notice")` | 收集类用 `form`/`image`/`file` 即可，**不需要新 kind** |
| `period` 枚举 | `("day", "week", "month")` | **⚠️ 只有三种周期，没有「不定期」** → ①的主要扩展点 |
| `period` 创建后不可改 | `app/state.py:1776` `PERIOD_IMMUTABLE` | — |
| 表单字段定义 | `schema_json`（JSON 数组） | H5 表单渲染直接用，**收集类任务可完全复用** |
| 采集规格 | `spec_json`（附件/图片/大小限制） | 同上 |
| 角色分组 | `role_ids`（JSON 数组，逗号分隔于 DB） | 平台任务靠角色圈人；**「不分人」是缺口** |

### 1.5 H5 收集链路完整

| 端点 | 作用 |
|---|---|
| `GET /h5/task` | 任务表单页 |
| `POST /api/h5/task/info` | 表单定义 |
| `POST /api/h5/task/upload` | 附件上传 |
| `POST /api/h5/task/submit` | 提交 |

**结论：①的「提交 H5」环节不需要新开发**，缺的只是「怎么生成一条属于本次触发的实例并把链接发出去」。

### 1.6 主动推送能力存在

`app/scheduler.py:192/306` `send_text(receive_id, text, idem_key)` —— 机器人能主动给指定用户发文本。

### 1.7 现有「统计」只有最粗的一层

`app/state.py:2207` 附近存在按 `kind != 'notice'` 过滤的统计口径；`task_instance` 表按
`(template_id, phone, period_key)` 唯一。

**⚠️ 这条唯一约束是第①项的关键卡点**，见 §2.3。

## 二、第①项：用户触发式任务（指令菜单）

### 2.1 用户描述的形态

- 后台定义「可以接受什么指令任务」，例如**安全信息收集** = 不定期、不分人
- 用户在**正常激活后**回复任意文本触发
- 机器人回复**任务列表**（编号 + 名称），用户选 `1` → 触发该任务的提交 H5

### 2.2 与现有 ack 的关系（复用点）

```
现状：任意文本 → 固定 ack（"看不懂聊天，不需要你回复文字"）
设计：任意文本 → 指令菜单（"回复数字选择任务 / 回复【指令查询】查看菜单"）
              ├─ 数字 N      → 触发第 N 个任务
              ├─ 【指令查询】 → 重发菜单
              └─ 其它文本    → 回菜单 + 一句"只认数字和指令查询"
```

用户明确提到要**加上「如需了解我的功能可以回复【指令查询】」** —— 这句应放进 ack 文案里，
让用户知道菜单可以随时调出来（避免用户发错一次就以为坏了）。

### 2.3 数据模型：需要新增什么

**核心矛盾**：现有 `task_instance` 唯一键是 `(template_id, phone, period_key)`，
`period_key` 是**日期**，`period` 只有 day/week/month。

用户要的「**不定期**」意味着：**同一个收集任务，同一个人，可以在任意多个时点各触发一次**，
每次都是一份独立数据。而现有模型里，同一模板同一人同一天**只有一条**实例。

#### 方案选择（需拍板）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 新增 `trigger_batch`** ⭐ | `task_instance` 加一列 `batch_key`（如 `trig_20261109_xxx`），唯一键改为 `(template_id, phone, batch_key)` | 复用现有实例/提交/审核全链路；「一次触发 = 一个批次」语义清晰；统计天然按批次聚合 | 需改唯一约束 + 相关查询 |
| B. 复用 `period_key` | 把 `period_key` 塞批次号（如 `B20261109_1`） | 零 schema 改动 | `period_key` 语义被污染，日期统计全乱 |
| C. 新建独立表 | `trigger_task` / `trigger_instance` | 不动现有模型 | 审核/提交/附件/提醒链路全要重做一遍 |

**我的建议：方案 A。** 理由：现有 `submission` 通过 `instance_id` 关联、`reminder_log`、
`upload_ref`、审核流程全都挂在 `task_instance` 上，方案 C 等于把整套复制一遍（且必然出现
"两边行为不一致"的长期维护债）。方案 B 看似最省，但 `period_key` 已经是"日期"语义，
塞批次号会让所有按日期的统计/看板/清理脚本集体失效。

> ⚠️ **这是本文第一个需要拍板的点。**

### 2.4 「不分人」怎么办

现有任务靠 `role_ids` 圈人（角色 → 成员）。用户要「安全信息收集」这种**不分人**的任务。

**设计**：新增任务类型 `trigger`（或 `kind` 不变、用 `period` 特殊值 + 独立标记），
其成员范围定义改为「全体已激活用户」而非某个角色组。

| 方案 | 说明 |
|---|---|
| A. 全体已激活用户 | 触发时按 `delivery_target` 取当前平台所有已激活用户，每人发一份菜单 |
| B. 后台指定名单 | 管理员手工圈一批人（复用现有成员池 UI） |
| C. 按角色组但允许「不限」 | `role_ids` 支持空数组 = 全体 |

**我的建议：A（全体已激活）+ 保留按平台隔离**（量子密信的激活用户不会收到企微菜单）。
理由：用户明确说"不分人"，且"安全信息收集"这类安全上报本就该全员可报。

> ⚠️ **这是第二个需要拍板的点。**

### 2.5 「不分人」与推送策略的冲突（重要风险）

**现有推送是"按周期给每个人建实例 + 定时推送"**。若收集任务是"用户主动触发"，
那它**没有推送时点** —— 推送变成了「用户发消息 → 机器人回菜单 → 用户选 → 机器人回 H5 链接」。

这带来一个必须想清楚的问题：

**用户不发消息，平台就不知道他需要填这张表。** 那这条收集任务的「完成率」怎么算？

- 分母是谁？触发过的用户？还是全员？
- 「触发率」和「完成率」是两个不同的指标（见 §3.3）

**我的建议**：把这类任务明确拆成两个独立指标 —— **触发率**（多少人主动问过）与
**完成率**（触发的人里填完的）。这正好也回答了用户 §3.2 的疑问（见 §3.3）。

### 2.6 指令菜单的内容

用户给的信息里，菜单至少要有：

```
【OPS任务调度助手】
请选择任务（回复数字）：
1. 安全信息提交
2. ……
回复数字触发任务；回复【指令查询】随时查看本菜单。
```

- 菜单由**后台配置**（用户说"在平台先定义可以接受什么指令任务"）
- 编号由后台配置时决定，**列表按配置顺序展示**
- 指令关键词（如【指令查询】）也应后台可配

### 2.7 边界情况清单

| 情况 | 建议处理 |
|---|---|
| 用户未激活就发文本 | 维持现状 → 回登记链接（`events.py:229`），**不变** |
| 用户发文本但平台无任何触发任务 | 回"当前没有可触发的任务，请联系管理员" |
| 用户选了一个不存在/已下线的编号 | 回"该任务已下线，请重新选择" + 重发菜单 |
| 用户选了一个他无权限的任务 | 回"该任务不在你的权限范围内" |
| 用户连点同一个编号 | **幂等**：同一批次内不重复建实例/重复发链接（复用 `idem_key` 机制） |
| 用户选编号后长时间不填 | 链接有效期问题（现有 H5 token 机制决定，见 §5） |

## 三、第②项：数据统计（让管理员一目了然）

### 3.1 现状与缺口

- 数据落在 `submission.fields_json`（+ `file_ref` 附件）
- 现有统计只到"按状态/周期/角色"的粗粒度（`app/state.py` 2207 附近）
- **没有**：按任务/批次/字段维度的聚合视图

### 3.2 统计形态的三档（按实现成本递增）

| 档 | 内容 | 成本 | 说明 |
|---|---|---|---|
| **L1 看板** | 每个收集任务一张卡：已触发人数 / 已提交数 / 完成率 / 附件数 | 低 | 复用现有 `InstanceStats` 口径，扩字段 |
| **L2 字段级** | 每个表单字段的分布（"安全隐患"选了 A 的 12 人、B 的 3 人） | 中 | 需解析 `fields_json`，按 `schema_json` 的字段定义对齐 |
| **L3 报表推送** | 生成统计结论 → **推送给指定用户（如领导）** | 中高 | 用户明确提到 |

### 3.3 用户问的"除了完成率，还该有什么"（我给的口径建议）

用户原话：「目前除了统计上传任务的完成率，谁未完成我不知道还有什么了。」

**建议的指标集**（分三类）：

**A. 进度类**
1. **触发率** = 触发过的人数 ÷ 目标人数（= 全体已激活用户）
2. **完成率** = 已提交 ÷ 已触发
3. **未完成名单**（人 + 部门 + 联系方式）—— 用户明确要的
4. **逾期未交**（如果该任务有截止时间）

**B. 质量类**
5. **附件齐全率** = 有附件的提交数 ÷ 提交数（安全类任务附件通常是刚需）
6. **字段完整率** = 关键字段无空值的提交数 ÷ 提交数
7. **异常值条数** = 超出取值范围/格式不合法的字段数（L2 才有意义）

**C. 趋势类**
8. **按批次/日期的提交曲线**（L1 就能出）
9. **首次响应时长**（从平台发菜单到用户提交，衡量任务是否被看懂）

> **我的建议：先只做 A 类（4 个指标）+ B 类的附件齐全率。** L2 字段级分布要等
> 「到底要统计什么字段」的口径稳定后再做 —— 用户自己也说"数据统计的模板我暂时还没有头绪"。
> **指标口径没定就先把字段级分布做出来，做完还得推翻重做。**

### 3.4 推送统计结果给领导（L3）

| 要素 | 建议 |
|---|---|
| 触发方式 | **复用现有 `send_text`**（`scheduler.py:192`），定时（周/月）自动推 |
| 收件人 | 后台配置（可多个用户/角色组），按平台分别投 |
| 内容形式 | 纯文本摘要（先不做图表/图片，避免依赖 `attach_image` 那条链路） |
| 权限 | 推送的是**统计结论**，不含个人敏感字段原文（安全类上报尤其要注意） |
| 审计 | 推送记录要留痕（谁、什么时候、推给谁、什么内容摘要） |

> ⚠️ **隐私边界建议**：给领导的推送默认只给**聚合数字 + 未完成名单**，
> 不给「某人具体填了什么」。若要明细，走单独的授权入口。

## 四、第③项：知识库接入（文档入库 + 向量检索问答）

### 4.1 定位

用户原话：「后续可能会接入知识库回答，帮用户回答文档入库后向量检索的问题。」

### 4.2 与本平台的关系（这是最需要想清楚的一点）

平台的机器人**面向内部员工**、且**只服务办公任务**。接入知识库后，它会变成一个
「什么都能问」的机器人 —— 这与 §2.2 里"我是任务调度助手，只负责按设定时间推送任务提醒"的
**自我定位直接冲突**。

**设计主张：知识库问答走独立的机器人入口，或明确改写机器人的定位文案。**
不要在同一个机器人里既说"我不懂聊天"、又能答知识库问题。

### 4.3 分期建议（明确建议先不做）

| 期 | 内容 | 理由 |
|---|---|---|
| **P0（本期不做）** | — | 用户自己说"后续可能会" |
| P1 | 文档入库（上传 → 解析 → 切块 → 向量化 → 入库） | 需要向量库选型（外部 API vs 本地） |
| P2 | 检索（用户提问 → 向量检索 → 取 top-k 片段） | — |
| P3 | 生成（片段 + 问题 → LLM 生成答案）+ 引用来源 | 需要确定 LLM 端点与成本归属 |
| P4 | 与平台结合：**「我提交的这条上报，制度依据是什么？」** | 这才是真正有价值的结合点 |

> **我的建议：把 P4 作为目标形态，P1-P3 只作为它的技术前置。**
> 纯通用问答对本平台的增量价值有限（员工有更好的通用 AI 工具）；
> 而「**结合平台已有的任务/上报数据做有上下文的回答**」是别处做不到的。

### 4.4 如果要做，几个必须先定的前提

| 待定 | 说明 |
|---|---|
| 向量库 | 外部 API（如某云向量库）vs 本地（pgvector / 独立服务）—— 影响成本与合规 |
| 文档来源与权限 | 谁能上传？入库文档的可见范围是否与提问者身份挂钩？ |
| 数据出域 | 文档内容是否允许发给外部 LLM？（涉密/个人信息风险） |
| 与现有"交付给 OA 的附件"的边界 | 已有约定：附件只收 docx/xlsx/zip/pdf —— 知识库入库格式是否沿用 |

## 六、明确不做 / 延后的（避免过度设计）

| 项 | 决定 | 理由 |
|---|---|---|
| 新建 `trigger_task` 独立表 | **不做** | 复用 `task_instance` + 加 `batch_key` |
| 触发式任务的定时推送 | **不做** | 触发式任务没有推送时点；用户自己来触发 |
