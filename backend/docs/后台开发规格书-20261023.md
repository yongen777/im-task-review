## 0. 一页读懂

### 0.1 这个系统做什么

管理员在后台定义**任务模板**（叫什么、发给哪些角色、几点提醒、几点截止、交什么、要不要审核）。
系统按时**主动私聊推送**给每位应完成的人；用户在 **H5 页面**提交（填表 / 传一张图 / 传一个附件）；
系统记录谁交了、谁没交、谁逾期，出统计并支持导出 xlsx。

### 0.2 与「群机器人」的根本区别（不要照抄旧实现）

| | 旧：群运维机器人 | 本系统 |
|---|---|---|
| 触发者 | 用户在群里 `@机器人 打卡` | **系统定时主动推** |
| 触达面 | 一个群，全员可见 | **一人一条私聊** |
| 业务 | 三种写死的业务 | **任意模板，后台可配** |
| 准入 | 群 + 名单 | **角色 + 手机号 + 激活状态** |
| 结构 | 群 → 业务 | 模板 → 角色 → 人 → 每人每周期一条实例 |

### 0.3 技术栈（照此执行）

| 项 | 选型 |
|---|---|
| 语言 | Python 3.11+ |
| Web 框架 | FastAPI + Uvicorn（单体双端口：业务与后台同进程） |
| 数据库 | SQLite（WAL 模式），单文件 `data/im_task.db` |
| 前端 | React 18 + Vite + TypeScript（构建产物由后端静态托管） |
| 样式 | 浅色、卡片式、企业后台风格；**不要**深色主题、不要渐变、不要大面积主色填充 |
| 定时 | 进程内调度循环（每 30 秒扫一次），不引入 Celery / Redis |
| 文件 | 本地磁盘 `data/uploads/`，不入对象存储 |
| 依赖 | 尽量少：`fastapi uvicorn httpx pycryptodome python-multipart openpyxl` |

### 0.4 三条铁律

1. **手机号是业务主键**。所有业务表只认手机号，平台 userId 只作为「投递地址」存在于一张映射表。
2. **后台界面不得出现任何外部用户 ID 输入框**。userId 由系统在用户激活时自动记录。
3. **字段、接口路径、状态取值必须与本文一致**。不要自行改名或增删枚举，后续会按本文写自动化验收。

## 1. 业务名词

| 名词 | 定义 |
|---|---|
| **任务模板** `task_template` | 一个业务定义：「日总结，发给渠道经理，17:30 提醒，18:00 截止，交一张截图，需审核」 |
| **角色** `role` | 一组人的集合，代表一种身份（领导 / 员工 / 渠道经理）。**同一角色内所有人适用相同模板** |
| **成员** `member` | 某个角色下的某个人，以手机号标识；人另有一个「部门」属性，与角色无关 |
| **实例** `task_instance` | 「某人在某周期该完成的一次任务」。唯一键 `(template_id, phone, period_key)` |
| **提交** `submission` | 实例对应的一次实际提交（表单值 / 一张图 / 一个附件） |
| **投递** `reminder_log` | 一次提醒的发送记录（计划时刻、实发、结果、重试次数） |
| **激活** | 用户在客户端向机器人发过至少一条消息，系统据此获得其平台 userId |
| **待办提醒（notice）** | 纯通知，如「每天 9 点提醒开会」：不生成实例、不进统计、无回执 |

### 1.1 周期 `period`

| period | period_key 格式 | 示例 | 截止归属 |
|---|---|---|---|
| `day` | `YYYY-MM-DD` | `2026-10-23` | 当天 |
| `week` | `YYYY-Www`（ISO 周，带连字符） | `2026-W43` | 周一~周日，归周一所在周 |
| `month` | `YYYY-MM` | `2026-10` | 自然月 |

> ISO 周必须用 **ISO 年**计算（2027-01-01 可能属于 2026-W53），周键格式固定 `%04d-W%02d`。

**锚点（`anchor_weekday` / `anchor_dom`）**：`day` 周期无需锚点，每天都触发；
`week` 必须配 `anchor_weekday`（1~7，1=周一），只有该星期几才生成实例；
`month` 必须配 `anchor_dom`（1~31），只有该日才生成；当月没有该日（如 2 月 31 日）时取**当月最后一天**。
截止时间 = 锚点日 + `deadline_offset` 天 的 `deadline` 时刻（默认 0，即当天）。

## 2. 两类用户与其完整旅程

### 2.1 管理员（登录后台的人）

**权限模型：所有登录管理员权限完全相同**（可建模板、改模板、删模板、看全部统计、代补交、催办）。
不设角色分级；一切写操作必须落 `admin_audit`。

主流程：

1. 建角色（领导 / 员工 / 渠道经理…）
2. 往角色里加人：**按部门批量导入**（Excel/CSV），或**单个添加**
3. 建任务模板：选提交类型、勾选适用角色、配提醒时刻与截止、配文案、勾是否需审核
4. 等系统按点推送；在「执行看板」看谁交谁没交
5. 对需审核的做通过/驳回；对没激活的人线下催；必要时代补交
6. 出统计、导出 xlsx

### 2.2 普通成员（不在后台里出现）

```
① 激活：客户端搜索机器人 → 发一句话 → 系统记录其 userId（绑定手机号）
        （此后才可能收到推送；未激活的人一律发不出去）
② 收提醒：到点收到私聊，正文里带 H5 链接
③ 点链接：打开 H5 → 填表 / 传图 / 传附件 → 提交
④ 若需审核：管理员驳回 → 立刻再收到一条私聊（含驳回原因 + 重交链接）→ 重新提交
⑤ 逾期未交：截止后 10 分钟收到一条逾期通知，72 小时内仍可补交
```

**关键约束（平台机制，不是可配置项）**：机器人只能给「已与其建立会话」的用户发消息。没有会话，发送接口返回 500。
因此「未激活」是必须被管理的状态，不是异常。

## 3. 业务规则（可逐条测试）

> 编号 Rxx 供验收引用。凡写「必须」，实现即不可省略。

### 3.1 模板

- **R01** 模板四类 `kind`：`form`（表单）、`image`（一张图）、`file`（一个附件）、`notice`（纯通知）。
- **R02** `form` 必须有 `schema_json`，字段 ≥1 个；字段类型限 `text | number | date | select`（`select` 带 `options`）。
- **R03** 每个字段属性：`key`（英文唯一）、`label`、`type`、`required`、`unit`（可选）、`max_len`（text，默认 200）、`options`（select 必填）。
- **R04** `image`/`file` 不需 `schema_json`，但可带一个可选说明字段（`allow_note=true` 时 H5 显示一句文本框）。
- **R05** 模板必须选 ≥1 个角色（`role_ids` 非空）；一个模板可关联多个角色。
- **R06** `period` 只能是 `day|week|month`，创建后不可改（改了会让历史实例口径错乱）。
- **R07** `need_review` 为真 → 提交后进 `submitted`，等管理员审核；为假 → 提交即 `approved`。
- **R08** 删除模板 = 软删（`deleted=1`）：停止后续调度，**历史实例与提交全部保留**，统计仍可查。
- **R09** 模板可停用（`enabled=0`）：与删除的区别是仍可在列表看到、可再启用。

### 3.2 提醒时刻（非通知类）

- **R10** `remind_at` 与 `deadline` 均为 `HH:MM`；**必须满足 `remind_at < deadline`**，否则保存时 400。
- **R11** 每个模板**只有一个提醒时刻**（不配多次）。到该时刻给「该周期所有未交的人」各发一条。
- **R12** 已交（`submitted`/`approved`）的人不再收到提醒。
- **R13** 到 `deadline` 仍未交 → 实例置 `overdue`。
- **R14** 截止后 **10 分钟**，对 `overdue` 且未发过逾期通知的人发 **1 次**逾期通知；不重复催。
- **R15** 停机补偿：若进程在该时刻未运行，重启后 **30 分钟内**补发一次；超过 30 分钟只记 `missed`，不再补发（避免深夜补发）。

### 3.3 待办提醒（notice）

- **R16** `notice` 只有：名称、文案、`notice_times`（1~3 个 `HH:MM`）、`role_ids`。
- **R17** `notice` **不生成实例、不进完成率统计**，只写 `reminder_log`（`kind='notice'`，`instance_id` 为 NULL）。
- **R18** `notice` 不做回执、不跟踪已读。唯一的可见信息是「已发 / 发送失败」。

### 3.4 实例与合并

- **R19** 实例唯一键 `(template_id, phone, period_key)`。**因此两个角色关联同一模板时，同一人只会有一条实例、只收一条提醒**。
- **R20** 不同模板**各自独立**生成实例、独立发提醒（一天可能收到多条，属预期）。
- **R21** 实例采用**惰性生成**：到提醒时刻为该模板该周期的所有在册成员批量生成（已存在则跳过）。这样人员变动不会污染历史周期。
- **R22** 实例生成时快照 `name_snap`/`dept_snap`，之后改人名或调部门**不影响历史**。
- **R23** 成员被移出角色：只影响**之后**生成的实例；已生成的实例仍按原状态存在，仍需被催办（除非管理员手动处理）。

### 3.5 提交与时限

- **R24** 补交窗口：**从 `deadline_at` 起算严格 72 小时**。窗口内 `overdue` 可提交；超窗口实例置 `expired`，**任何人（含管理员）都不可再提交**。
- **R25** 逾期提交有效，但 `late_submit=1`，导出时标「逾期补交」。
- **R26** 管理员代补交：`source='admin'`，必须写审计；**同样受 72 小时窗口约束**。
- **R27** 驳回后重交窗口：取「原截止 +72h」的**剩余时间**；若剩余不足 24 小时，**保底给 24 小时**（从驳回时刻起算）。
- **R28** 重交时旧的 `submission` 保留（追加一条新记录），审核只看最新的那条。
- **R29** 每个实例最终只有一条「有效提交」= 最新一条 `status != rejected` 的记录。

### 3.6 审核

- **R30** 需审核的实例：`submitted` → 通过 `approved` / 驳回 `rejected`。
- **R31** 驳回必须填写原因（≥2 字），并**立即**给该用户推一条私聊，内容含驳回原因与重交 H5 链接。
- **R32** 驳回后实例回到「待完成」语义（可重交），但仍显示 `rejected` 历史次数。

### 3.7 文件

- **R33** 白名单（扩展名）：`pdf doc docx xls xlsx ppt pptx zip jpg png`。**`.md` 明确不支持**。
- **R34** 大小：普通附件 ≤20MB，图片 ≤9MB。
- **R35** MIME 必须服务端嗅探（读文件头），**不信任客户端声明的 Content-Type**；嗅探结果不在白名单 → 400。
- **R36** 每个实例**只允许一个文件**（`submission.file_ref` 单值）。需要多份就让管理员多开一个模板。
- **R37** 文件落盘路径：`data/uploads/<period_key>/<template_id>/<ref>.<ext>`，库里只存相对路径。
- **R38** 物理文件保留 **180 天**，到期只删文件；`submission` 记录永久保留（保留文件名、大小、时间、mime）。

### 3.8 人员与激活

- **R39** 手机号格式 `^1[3-9]\d{9}$`，否则 400「手机号格式不正确」。
- **R40** 同一角色内手机号唯一；跨角色可重复（一人可属多角色）。
- **R41** 激活记录写入 `delivery_target(platform, phone, external_id)`；同一手机号重复激活则更新 `last_event_at`。
- **R42** 未激活判定：`delivery_target` 中查不到该手机号。此时**不发送**，写入「未激活名单」。
- **R43** 部门批量导入：先 `dry_run` 返回差异（新增 N / 已存在 M / 格式错误 K 行及行号），确认后才落库。

### 3.9 权限与审计

- **R44** 未登录访问 `/api/admin/*` 返回 401；访问 `/groups` 等后台页面 303 跳 `/login`。
- **R45** 所有写接口校验 CSRF 头 `X-CSRF-Token`（从 `/api/admin/me` 取），缺失或错误 403。
- **R46** 审计动作至少覆盖：登录、登出、改密、模板增改删、角色增改删、成员增删改、批量导入、审核、代补交、手动催办、导出。

### 3.10 周期锚点与说明字段（v1.1 补）

- **R47** `allow_note` 是 `task_template` 的独立布尔列（默认 0）。为 1 时 H5 在提交区下方显示一个可选文本框，内容写入 `submission.note`（≤200 字）。⛔ 不要存进 `schema_json`，它是模板级开关，不是字段。
- **R48** 周/月模板必须配锚点：`period=week` → `anchor_weekday` 必填且 ∈1..7；`period=month` → `anchor_dom` 必填且 ∈1..31；`period=day` 时两个字段必须为空。截止时刻 = **锚点日 + `deadline_offset` 天** 的 `deadline`；`deadline_offset` 取值 0~6，默认 0。
- **R49** 锚点日决定 `period_key` 归属：周模板的 `period_key` 取**锚点所在 ISO 周**；月模板取**锚点所在月**；跨月/跨年的锚点（如 `anchor_dom=31` 落到 2 月末）仍归该月。

## 4. 数据模型（SQLite，照此建表）

**表数口径（精确版）**：共 **14 张表** = 10 张业务表（`scope` `role` `member` `delivery_target`
`task_template` `task_instance` `submission` `reminder_log` `upload_ref` `h5_token`）
+ 3 张支撑表（`admin_user` `admin_session` `admin_audit`）+ 1 张版本门表（`schema_version`）。
⛔ 版本门表不计入业务表；下文编号 1~12 是**分组编号**，不是表数（第 11 组含两张表）。

```sql
PRAGMA journal_mode=WAL;

-- 1 主体：P0 只有一条根记录（预留多部门/多租户）
CREATE TABLE scope (
  scope_id   TEXT PRIMARY KEY,
  name       TEXT NOT NULL,
  type       TEXT NOT NULL DEFAULT 'dept',   -- dept | group
  parent_id  TEXT,
  created_at TEXT NOT NULL
);

-- 2 角色：平铺，⛔ 不挂在部门下（领导角色要能跨部门加人）
CREATE TABLE role (
  role_id    TEXT PRIMARY KEY,               -- 'r_' + 8 位随机
  name       TEXT NOT NULL UNIQUE,
  note       TEXT,
  created_at TEXT NOT NULL
);

-- 3 角色成员
CREATE TABLE member (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  role_id    TEXT NOT NULL,
  phone      TEXT NOT NULL,                  -- ^1[3-9]\d{9}$
  name       TEXT NOT NULL,
  dept       TEXT,                           -- 人的组织属性，与角色无关
  enabled    INTEGER NOT NULL DEFAULT 1,
  source     TEXT NOT NULL DEFAULT 'manual', -- manual | import
  created_at TEXT NOT NULL,
  UNIQUE(role_id, phone)
);

-- 4 投递地址：手机号 ↔ 平台 userId（激活时自动写入）
CREATE TABLE delivery_target (
  platform      TEXT NOT NULL DEFAULT 'zdxlz',
  phone         TEXT NOT NULL,
  external_id   TEXT NOT NULL,
  activated_at  TEXT NOT NULL,
  last_event_at TEXT NOT NULL,
  PRIMARY KEY (platform, phone)
);

-- 5 任务模板
CREATE TABLE task_template (
  template_id TEXT PRIMARY KEY,              -- 't_' + 8 位随机
  name        TEXT NOT NULL,
  kind        TEXT NOT NULL,                 -- form | image | file | notice
  role_ids    TEXT NOT NULL,                 -- JSON 数组
  schema_json TEXT,                          -- 仅 form
  text_tpl    TEXT NOT NULL,                 -- 支持 {姓名}{部门}{任务名}{截止时间}
  remind_at   TEXT,                          -- 仅非 notice
  notice_times TEXT,                         -- 仅 notice，JSON 数组
  deadline    TEXT,                          -- 仅非 notice
  period      TEXT NOT NULL,                 -- day | week | month
  need_review INTEGER NOT NULL DEFAULT 0,
  max_file_mb INTEGER,                       -- 空=默认（图片 9 / 其他 20）
  allow_note     INTEGER NOT NULL DEFAULT 0, -- 1=H5 额外显示一句可选说明框（R04）
  anchor_weekday INTEGER,                    -- 仅 period=week：1~7（1=周一）
  anchor_dom     INTEGER,                    -- 仅 period=month：1~31（当月无此日取月末）
  deadline_offset INTEGER NOT NULL DEFAULT 0,-- 截止 = 锚点日 + N 天（R48）
  enabled     INTEGER NOT NULL DEFAULT 1,
  deleted     INTEGER NOT NULL DEFAULT 0,
  created_by  TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

-- 6 实例
CREATE TABLE task_instance (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  template_id   TEXT NOT NULL,
  phone         TEXT NOT NULL,
  name_snap     TEXT NOT NULL,
  dept_snap     TEXT,
  period_key    TEXT NOT NULL,
  status        TEXT NOT NULL,   -- pending|submitted|approved|rejected|overdue|expired
  deadline_at   TEXT NOT NULL,
  created_at    TEXT NOT NULL,
  submitted_at  TEXT,
  reviewed_at   TEXT,
  reviewer      TEXT,
  reject_reason TEXT,
  reject_count  INTEGER NOT NULL DEFAULT 0,
  late_submit   INTEGER NOT NULL DEFAULT 0,
  UNIQUE(template_id, phone, period_key)
);
CREATE INDEX ix_inst_status  ON task_instance(status, deadline_at);
CREATE INDEX ix_inst_period  ON task_instance(period_key);

-- 7 提交（追加式，不覆盖）
CREATE TABLE submission (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  instance_id INTEGER NOT NULL,
  fields_json TEXT,
  file_ref    TEXT,
  file_name   TEXT,
  mime        TEXT,
  size        INTEGER,
  note        TEXT,
  source      TEXT NOT NULL,   -- user | admin
  status      TEXT NOT NULL,   -- submitted | approved | rejected
  created_at  TEXT NOT NULL
);
CREATE INDEX ix_sub_inst ON submission(instance_id, id);

-- 8 提醒投递
CREATE TABLE reminder_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  template_id TEXT NOT NULL,
  instance_id INTEGER,          -- notice 为 NULL
  phone       TEXT NOT NULL,
  kind        TEXT NOT NULL,    -- remind|overdue|reject|manual|notice
  planned_at  TEXT NOT NULL,
  sent_at     TEXT,
  result      TEXT NOT NULL,    -- sent|failed|skipped|missed
  error       TEXT,
  retry       INTEGER NOT NULL DEFAULT 0,
  idem_key    TEXT NOT NULL UNIQUE
);

-- 9 上传引用
CREATE TABLE upload_ref (
  ref         TEXT PRIMARY KEY,
  phone       TEXT NOT NULL,
  template_id TEXT,
  file_name   TEXT NOT NULL,
  mime        TEXT NOT NULL,
  size        INTEGER NOT NULL,
  rel_path    TEXT NOT NULL,
  consumed    INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL
);

-- 10 H5 令牌（只存哈希）
CREATE TABLE h5_token (
```

## 5. 状态机

```
实例 task_instance
  pending ──提交(需审核)──> submitted ──通过──> approved   [终态·完成]
     │                        └──驳回──> rejected ──重交──> submitted
     ├──提交(免审核)──────────────────────────> approved
     ├──过 deadline────────────────> overdue ──窗口内补交──> submitted / approved
     │                                  └──超 72h──> expired  [终态·不可补交]
     └──（overdue 也可被管理员代补交，同样受窗口约束）

提交 submission
  submitted（待审） → approved（通过）/ rejected（驳回）
  免审核时直接 approved
```

**判定优先级**（每分钟一次的巡检，顺序不可变）：

1. `pending` 且 `now > deadline_at` → `overdue`
2. `overdue` 且 `now > deadline_at + 72h` → `expired`
3. `rejected` 且 `now > 重交截止` → `expired`（重交截止见 R27）
4. 已完成态（`approved`）永不回退

## 6. 定时调度

### 6.1 循环

每 **30 秒**执行一次，单实例、单线程（SQLite 写入串行，避免锁竞争）：

```
每分钟（整分钟触发一次）：
  A. 生成实例：对每个 enabled=1 且 deleted=0 且 kind!=notice 的模板，
     若「今天命中锚点」且 now 的 HH:MM == remind_at（且本分钟未执行过）：
         命中锚点 := period=day  → 恒真
                    period=week → now.isoweekday() == anchor_weekday
                    period=month→ now.day == min(anchor_dom, 当月天数)
         for m in 该模板所有角色的所有 enabled 成员：
             ensure_instance(template, m, period_key(now))   # UNIQUE 保证幂等
  B. 发提醒：对步骤 A 生成的、且状态仍为 pending 的实例：
         target = delivery_target(phone)
         无 target → 记 skipped/未激活，跳过
         有 target → 发送 → 写 reminder_log
  C. 逾期扫描（每 5 分钟一次）：
         逾期通知：status=overdue 且未发过 kind=overdue → 截止+10min 后发 1 次
         状态推进：按 §5 的优先级批量更新
  D. 通知类：kind=notice 且 now 的 HH:MM 命中 notice_times → 逐个发送 → 记 reminder_log
  E. 文件清理（每天 03:00）：超过 180 天的物理文件删除，submission 记录保留
```

### 6.2 幂等

```
idem_key = sha1(f"{template_id}|{phone}|{period_key}|{kind}|{seq}")
seq: 1=未完成提醒 2=逾期通知 3=驳回重交 4+=手动催办
```
`reminder_log.idem_key` 建 UNIQUE；插入冲突即视为「已发过」，直接跳过。
**重启后不得重复发送**，这是硬性验收项。

### 6.3 发送失败处理

- 每个目标最多重试 3 次，间隔 30 秒 / 2 分钟 / 5 分钟。
- 3 次仍失败 → `result='failed'` + 记 `error`，进「发送失败」列表（后台可见）。
- 发送速率 ≤10 条/秒，避免触发平台风控。

### 6.4 手动催办

后台对单条实例点「催办」→ 立即发送（`kind='manual'`，`seq` 递增），不受 `remind_at` 限制，但同一实例 10 分钟内只允许一次。

## 7. 通道集成（量子密信 open-apis）

> 以下均为**已验证结论**，实现时直接按此写，不要自行探索。

### 7.1 取访问令牌

```
POST https://imtwo.zdxlz.com/open-apis/v1/auth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=<APP_ID>&client_secret=<APP_SECRET>

→ 200 {"access_token":"...","expires_in":7199,...}
```

- 内存缓存 token，剩余有效期 <300 秒时刷新。
- ⚠️ **不要**用 `/seal/oauth2/token`：它签发的是另一套 JWT，在 `/open-apis/*` 一律 401。

### 7.2 发送单聊文本

```
POST https://imtwo.zdxlz.com/open-apis/v1/messages/v1/send
Authorization: Bearer <access_token>
X-Client-Id: <APP_ID>                       ← 必需；缺了会 500
Content-Type: application/json; charset=utf-8

{
  "receive_id": "<external_id，19 位数字>",
  "msg_type": "text",
  "content": "{\"content\":\"消息正文\"}",     ← 注意：是 JSON 字符串，不是对象
  "idem_key": "<幂等键>"
}

→ 200 {"success":true,"code":200,"message":"SUCCESS"}
```

**错误处理约定**：

| 现象 | 含义 | 处理 |
|---|---|---|
| 200 且 `success=true` | 已受理 | 记 `sent` |
| 500 `INTERNAL_SERVER_ERROR` | **该用户与机器人无会话** | 记 `failed`，置「未激活/需激活」，不重试 |
| 401 | token 失效 | 刷新 token 后重试 1 次 |
| 其他 4xx | 参数或权限问题 | 记 `failed` + error 原文 |

> 200 只代表「受理」，不代表「已读」。系统不追踪已读。

### 7.3 事件订阅（收：用于获得 userId）

平台以 HTTP POST 推送到本服务的 `/api/app-events`：

```
Header: X-CTQ-Timestamp（毫秒字符串）
        X-CTQ-Nonce
        X-CTQ-Signature（64 位 hex）
Body:   纯 base64 密文字符串（不是 {"data": ...} 包装）
```

**验签**（时间/nonce/body 都被签名覆盖）：

```python
sig = hmac.new(verify_token.encode(), (ts + nonce + body).encode(), hashlib.sha256).hexdigest()
assert hmac.compare_digest(sig, signature)   # 不等 → 401
```

**解密**：

```python
key = hashlib.sha256(f"{encrypt_key}:{ts}:{nonce}".encode()).digest()   # 32 字节
raw = base64.b64decode(body)
iv, ct = raw[:16], raw[16:]
plain = unpad(AES.new(key, AES.MODE_CBC, iv).decrypt(ct), 16)
event = json.loads(plain)
```

⚠️ `encrypt_key` 必须用**后台配置页给出的原始字符串**参与拼接；**不要**先做 base64 解码（做了就解不开）。

**事件体关键字段**：

```json
{"appId":63474,"loginId":"<APP_ID>","eventType":"callback:direct",
 "userId":"3000000000000000001","groupId":"","toUserId":"8602191574774345334",
 "msgUid":"...","content":{"content":"你好"}}
```

- `userId` = 发送人 → 写入/更新 `delivery_target.external_id`
- `toUserId` = 机器人自己（**不要**当收件人）
- `loginId` = APP_ID
**激活路径（三条，实现时三条都要有）**

| 路径 | 触发 | 处理 | 适用 |
|---|---|---|---|
| A 自动 | 事件体里带手机号 | 直接按手机号写 `delivery_target` | 首选，无需用户操作 |
| B 私聊自报 | 用户私聊机器人发送 11 位手机号（`^1[3-9]\d{9}$` 且整条消息只有号码） | 做护栏校验后绑定，并回执 | 平台事件不带手机号时的主要路径 |
| C 绑定页 | 管理员下发 `/h5/bind` 链接（带一次性令牌），用户在网页填手机号 | 校验后绑定 | B 失败或用户嫌麻烦时兜底 |

**B/C 路径的三条护栏（防冒绑，缺一不可）**

1. 该手机号**必须已存在于 `member` 表**（= 管理员已导入），否则拒绝：「该号码不在任何任务名单中，请联系管理员」；
2. 该手机号**必须尚未绑定**（`delivery_target` 无记录）；已绑定则拒绝：「该号码已绑定，如需变更请联系管理员」，⛔ 不允许覆盖；
3. 绑定成功回执必须带**脱敏号码**与申诉提示：「已绑定手机号 138****0099，若非本人操作请联系管理员」，并写 `admin_audit`（`action='target.bind'`）。

> 管理员可在「未激活名单」页对单个手机号执行「解除绑定」（`action='target.unbind'`），用于换号或错绑纠正。

**响应的优先级**：进入激活判断前必须先验签；验签失败的请求一律 401，不得进入绑定逻辑。

**响应**：始终返回 `{"success":true,"code":200,"message":"OK"}`（除验签失败返回 401）。

## 8. H5 页面规格（用户侧）

### 8.1 入口与令牌

- 提醒正文里的链接形如：`https://<host>/h5/task#t=<令牌明文>`
- **令牌放 URL fragment（`#` 后），不放 query**，避免进服务器日志与 Referer。
- 令牌由服务端签发：绑定 `手机号 + 模板 + 周期 + 实例`，有效期 **72 小时**，首次成功提交后作废。
- 页面加载时 JS 读取 `location.hash`，POST 到 `/api/h5/task/info` 换取任务详情。

### 8.2 页面结构（移动端优先，单列，最大宽度 480px）

```
┌ 顶部：任务名 + 截止时间（已逾期则红字「已逾期，可补交」）
├ 状态条：待提交 / 待审核 / 已通过 / 已驳回（显示驳回原因）
├ 正文：提醒文案（同私聊内容，纯文本）
├ 提交区：
│   form  → 按 schema 逐字段渲染
│   image → 一个大按钮「拍照或选择图片」+ 预览 + 删除
│   file  → 一个按钮「选择文件」+ 文件名/大小 + 删除
├ 可选说明（allow_note）
└ 底部按钮：「提交」（提交后置灰，显示结果）
```

### 8.3 校验（前端拦 + 后端校验，缺一不可）

| 场景 | 文案 |
|---|---|
| 必填未填 | 「请填写{字段名}」 |
| 数字非数字 | 「{字段名}只能填数字」 |
| 文件类型不符 | 「不支持该文件类型，请上传 PDF/Word/Excel/PPT/压缩包/图片」 |
| 文件过大 | 「文件超过 {N}MB，请压缩后重试」 |
| 已过期 | 「该任务已超过补交期限（72 小时），无法提交」 |
| 已通过 | 「该任务已提交成功，无需重复提交」 |

### 8.4 提交结果

- 提交成功 → 展示「提交成功」+ 状态（待审核/已完成），按钮变为不可点。
- 需审核 → 文案「已提交，等待审核」。
- 免审核 → 文案「已完成」。

## 10. 后台页面规格

> 布局：左侧导航（概览 / 任务模板 / 角色与人 / 执行看板 / 未激活 / 统计 / 审计 / 账号），右侧内容区。顶部右侧显示当前账号与「安全退出」。

### 10.1 概览

- 四张卡片：今日应完成、今日已完成（含完成率）、逾期未交、未激活人数。
- 下方两块列表：「今日待审核」（前 10 条，可点进审）、「发送失败」（前 10 条，带原因）。
- 若通道未配置或密钥缺失，顶部红色提示条：「消息通道未配置，定时提醒不会发送」。

### 10.2 任务模板

- 列表列：名称、类型（表单/图片/附件/通知）、适用角色、提醒时间、截止、周期、需审核、状态、操作。
- 操作：编辑 / 停用·启用 / 删除 / **预览影响人数**（弹窗显示 应发 N 人、已激活 M、未激活 K）。
- 编辑页分四段：基本信息 → 提交内容（按类型切换表单设计器 / 图片 / 附件）→ 时间规则（周期 + **锚点** + 提醒时刻 + 截止 + 截止偏移天数）→ 提醒文案（带变量插槽按钮，右侧实时预览）。
- 时间规则段的联动：选「每周」时出现星期选择器（周一~周日），选「每月」时出现 1~31 日选择器（提示「当月无此日则取月末」），选「每天」时两者隐藏；`deadline_offset>0` 时在截止时间旁提示「即锚点后第 N 天」。
- 表单设计器：可增删字段，字段行内可选类型、必填、单位、字数上限；`select` 可编辑选项。
- 校验即时反馈：`remind_at` 不早于 `deadline` 时字段下方红字提示，保存按钮禁用。

### 10.3 角色与人

- 左栏角色列表（含人数），顶部「+ 新建角色」；右栏该角色成员表。
- 成员表列：姓名、手机号、部门、激活状态（绿点已激活 / 灰点未激活）、来源、操作（编辑 / 移出）。
- 顶部按钮：「+ 添加成员」、「批量导入」。
- 批量导入弹窗三步：上传文件 → **差异预览**（新增 N / 已存在 M / 错误 K，错误列出行号与原因）→ 确认导入。
- 移出确认弹窗文案：「移出后该成员不再收到本角色后续任务；已产生的历史记录与待完成的当前任务不受影响。」

### 10.4 执行看板

- 筛选：日期（默认今天）、模板、状态、关键字（姓名/手机号）。
- 表格列：姓名、部门、手机号、任务、状态徽章、截止、提交时间、审核人、操作。
- 状态徽章配色：待完成（灰）、待审核（蓝）、已通过（绿）、已驳回（橙）、已逾期（红）、已过期（深灰）。
- 行内操作：查看（详情抽屉）、代补交、通过、驳回、催办。
- 详情抽屉：基本信息 + 提交内容（表单值表格 / 图片缩略图可点开 / 附件下载）+ 审核记录 + 投递记录（时刻、结果、重试次数）。
- 空态：「当前筛选条件下没有记录」。

### 10.5 未激活名单

- 按角色分组列出未激活人员（姓名、手机号、部门、所属角色）。
- 顶部：「导出名单」（xlsx）、说明文案：「这些人尚未在客户端与机器人建立会话，暂时收不到提醒，请线下通知其搜索机器人并发送任意消息。」

### 10.6 统计

- 时间范围选择（近 7 天 / 近 30 天 / 自定义）。
- 完成率趋势（按日折线）、按模板完成率（横向条形）、按人明细（表格，可排序）。
- 右上「导出 xlsx」。

### 10.7 审计

- 表格：时间、操作人、动作、对象、详情（可展开 JSON）。
- 支持按操作人与时间范围筛。

### 10.8 账号

- 修改密码（旧密码 + 新密码 + 确认）。
- 展示当前登录账号与上次登录时间。

### 10.9 通用要求

- 所有删除/驳回/移出必须二次确认弹窗，确认按钮为危险色。
- 所有操作完成给 toast（成功绿 / 失败红）。
- 空态、加载态、错误态三态齐全；禁止空白页。
- 表格分页；列表加载失败可重试。

## 12. 非功能要求

| 项 | 要求 |
|---|---|
| 时区 | 固定 `Asia/Shanghai`，不受操作系统时区影响 |
| 并发 | 单进程；SQLite 开启 WAL，写操作串行；禁多 worker |

## 16. 实现反馈补丁（v1.2 · 2026-10-23）

阶段一代码评审后需固化的 7 条。**与前述条款冲突时，以本节为准。**

| # | 事项 | 要求 |
|---|---|---|
| **P1** | `.env` 加载 | 服务启动时读取项目根 `.env`（`python-dotenv`）；文件不存在则只读系统环境变量。⛔ 密钥不得写进代码或前端 |
| **P2** | `must_change` 服务端强制 | 会话 `must_change=1` 时，除 `GET /api/admin/me`、`POST /api/admin/change-password`、`POST /api/admin/logout` 外，其余 `/api/admin/*` 一律返回 `403 MUST_CHANGE_PASSWORD`。⛔ 不能只在前端跳转 |
| **P3** | `/healthz` 增加 `crypto` | 返回 `{"status","db","channel","crypto"}`；`crypto` = `ok / unconfigured`（取决于 `IMT_ENCRYPT_KEY` 与 `IMT_VERIFY_TOKEN` 是否齐全）。`crypto=unconfigured` 时后台须显著提示「事件回调不可用，激活链路中断」 |
| **P4** | 发送成功判定 | `success == true \|\| code == 0 \|\| code == 200` 三者取或；**仅 HTTP 200 不算成功**（平台会在 body 里带业务码） |
| **P5** | `scripts` 包 | 补 `scripts/__init__.py`（空文件），保证 `python -m scripts.create_admin` 在任意工作目录可用 |
| **P6** | `schema_version` 归属 | 全库共 **14 张表** = 10 业务 + 3 支撑 + 1 版本门。台账与验收按此表述；⛔ 版本门不计入业务表，⛔ 不要写「12 张表」（第 11 组含 `admin_user` 与 `admin_session` 两张） |
| **P7** | 公网地址 | `IMT_PUBLIC_BASE_URL` 用于拼 H5 链接，**必填无默认**。当通道已配置而该值仍是 `127.0.0.1` / `localhost` 时，启动打 **WARN** 日志 |
| **P8** | 端口无默认值 | `IMT_PUBLIC_PORT` / `IMT_ADMIN_PORT` **必须显式配置**。缺失时启动直接失败退出，打印「未配置端口，请向运维申请」。⛔ 代码中不得出现任何端口字面量（含 `12334`、`18003`、`8000`），`.env.example` 里留空并注明"由运维分配" |
| **P9** | 公网地址格式校验 | `IMT_PUBLIC_BASE_URL` 除非空外，还须校验 scheme ∈ {http, https} 且有 host；不合法同样按「未配置端口」处理并退出。⛔ 否则用户写成 `1.2.3.4:18001`（漏 scheme）时能启动，但 H5 链接点开是坏链接 |
| **P10** | 两端口不得相同 | `IMT_PUBLIC_PORT == IMT_ADMIN_PORT` 时启动直接失败，提示「业务端口与后台端口不能相同」。⛔ 否则报的是 `address already in use`，看不出真因 |
| **P11** | 退出信息只打一次 | 缺端口时**只保留一种**输出方式（`print` 到 stderr 或 `raise SystemExit(msg)` 二选一），⛔ 不要两者都做，否则终端上同一句话出现两遍 |

**两条归属补充（封面版本遗漏）**

- `POST /api/app-events`（事件回调）归 **阶段二**。它是激活的唯一入口，缺它整条推送链路不成立。
- 后台静态托管与 `/login` 外壳归 **阶段二**。在此之前后台端口根路径返回 404 属正常，不算缺陷。

**新增错误码**

| code | HTTP | 含义 |
|---|---|---|
| `MUST_CHANGE_PASSWORD` | 403 | 首次登录未改密，除改密/登出/me 外的接口一律拒绝 |
