## 1. 这是什么

**通用 IM 办公任务调度平台**：以量子密信为起点，管理员在后台定义任务模板（谁、什么时间、提交什么、要不要审核），系统按时点对点推送到人，用户在 H5 里提交，后台出统计。

与现有「群运维机器人」的根本区别：

| | 群运维机器人（已上线） | 本平台 |
|---|---|---|
| 触发 | 用户主动发「@机器人 打卡」 | **后台定时触发** |
| 形态 | 群里公开 | **点对点单聊** |
| 业务 | 三种写死的业务（打卡/总结/报数） | **任意模板，后台可配** |
| 扩展 | 仅量子密信群 | 预留企业微信/飞书/钉钉 |

一句话：**从「群 × 三种固定业务」变成「主体 × 任意模板 × 每人每周期一个实例」。**

## 3. 已定口径（合并两轮，共 24 条，全部生效）

### 3.1 任务与提交

| # | 定档 |
|---|---|
| 1 | **提交类型三选一**：表单（H5 填写字段）/ 图片 / 附件。**表单走 H5 动态渲染字段**，字段定义在模板里（类型建议：文本、数字、日期、单选、多选） |
| 2 | 每个任务**只支持单个图片或单个附件**；需要多个就让管理员多开一个业务 |
| 3 | 附件白名单：`pdf doc docx xls xlsx ppt pptx zip jpg png`；单文件 ≤ **20MB**，图片 ≤ **9MB**；MIME 必须服务端嗅探，**不信客户端声明** |
| 4 | 每个模板可配 **是否需要审核**：不需要 → 提交即入库（`approved`）；需要 → `submitted` 等审 |
| 5 | 审核驳回 → **立即单聊推送驳回原因 + 重交 H5 链接** |
| 6 | 数据库记录**永久保留**；本地磁盘文件保留 **180 天**，到期**只删物理文件**，记录里保留文件名/大小/时间 |

### 3.2 提醒（两类，互不混用）

| # | 定档 |
|---|---|
| 7 | **未完成提醒**：在模板里定义，**只配一个时刻** `remind_at`，**必须早于截止**（`remind_at < deadline`）；过截止即置逾期 |
| 8 | **逾期提醒**：截止后 **10 分钟**向未交人员发 **1 次**，不反复催 |
| 9 | **待办事务提醒（notice）**：如「每天 9 点提醒某领导开会」，只有时刻 + 文本 + 收件人；**不生成实例、不进统计、不做回执**，P0 只记「已发 / 已送达」 |
| 10 | 同一人命中同一 `template_id`（不论来自几个角色）→ **实例唯一，只发一条**；不同模板**各自独立触发** |

### 3.3 时限与状态

| # | 定档 |
|---|---|
| 11 | 补交窗口：**从截止时刻起严格 72 小时**，超时置 `expired` 锁定，不可补交 |
| 12 | 逾期期间允许**用户自助补交**，也允许**后台代补交**（带操作人留痕），均标记「逾期补交」 |
| 13 | 驳回重交：给予「原截止 +72h」的**剩余时间**；不足 24h 时**保底 24h** |

### 3.4 组织与权限

| # | 定档 |
|---|---|
| 14 | **角色 = 业务集合**（领导 / 员工等），可由管理员逐个加人；**也支持按部门批量导入** |
| 15 | **角色与部门是两个维度**：部门是人的属性，角色是业务范围。⛔ 不要把角色做成部门的子节点——否则「领导角色跨部门加人」做不到 |
| 16 | 员工一般不多角色；若多角色，**两个角色的全部业务都触发**（同一模板仍按 #10 合并） |
| 17 | 后台：**登录管理员均有全部权限**（改模板、看统计、代补交）；依靠 `admin_audit` 留痕，不设角色分级 |
| 18 | 人员标识：**手机号是业务主键**；平台 userId 由激活时自动绑定，人工不介入 |

### 3.5 触达与上线

| # | 定档 |
|---|---|
| 19 | 机器人**不走群聊**：用户在客户端搜索机器人名（或工作台）→ 发一句话 → 激活会话，之后才能收到推送 |
| 20 | **未激活的人发不出去**，后台必须标状态并可导出名单，由管理员人工催 |
| 21 | 应用可见范围：开发到差不多阶段放开**全员**（⚠️ 原定「需单位管理员审核，提前一周」；**2026-10-26 业务方确认本人持有该权限、可随时调整**，这项不再卡进度） |

| 23 | 名称：**通用 IM 办公任务调度平台**；代码目录 `im-task`；英文代号 `IMTask` |
| 24 | 交付节奏：P0 先跑通「模板 → 定时提醒 → 提交 → 统计」；P1 补审核/逾期/重交/导出/投递回执 |

## 4. 数据模型（8 张表，SQLite 配置 + 业务）

> 设计取舍：配置与业务**同库不同表**（新项目不学 group-ops 的 SQLite+MySQL 双库，除非将来必须接甲方业务库）。

```
scope            (scope_id PK, name, type[dept|group], parent_id, created_at)
role             (role_id PK, name, note, created_at)          -- 平铺，不挂部门
member           (id PK, role_id, phone, name, dept, enabled, source, created_at)
                  UNIQUE(role_id, phone)
delivery_target  (platform PK, phone PK, external_id, activated_at, last_event_at)
                  -- 手机号 ↔ 平台 userId，激活时自动写

task_template    (template_id PK, name, kind[form|notice],
                  role_ids JSON, submit_fields JSON, file_policy JSON,
                  remind_at, deadline, period[day|week|month],
                  need_review, text_tpl, enabled, created_by, created_at)
task_instance    (id PK, template_id, phone, period_key,
                  status, deadline_at, created_at, submitted_at,
                  reviewed_at, reviewer, reject_reason)
                  UNIQUE(template_id, phone, period_key)      -- ← #10 的合并靠这条
submission       (id PK, instance_id, fields_json, file_ref, file_name,
                  mime, size, source[user|admin], status, created_at)
reminder_log     (id PK, template_id, instance_id NULL, phone, kind,
                  planned_at, sent_at, result[sent|delivered|failed],
                  error, retry, idem_key)
```

三条设计理由（别在新会话里推翻）：

1. **实例落在「人 × 周期」**，不是「模板 × 人」。统计按周期出，成员变动后历史不能跟着变。
2. **`reminder_log` 与 `submission` 分开**。同一件事「发了三次、第三次才交」要能还原，否则永远说不清是系统没发还是人没交。
3. **`period_key` 格式固定**：日 `2026-10-23`、周 `2026-W43`（ISO 周，带连字符）、月 `2026-10`。

## 5. 触发链路

### 5.1 三层绑定（缺一层就发不出去）

| 层 | 绑定什么 | 谁维护 |
|---|---|---|
| ① 业务范围 | `task_template.role_ids` ↔ 角色 | 管理员建模板时勾选 |
| ② 人 | 角色 ↔ `member.phone` | 管理员加人（部门批量 / 单个） |
| ③ 地址 | `phone` ↔ `delivery_target.external_id` | **系统自动**（激活时写） |

### 5.2 调度主循环

```python
for tpl in due_templates(now):                      # 到点的模板（remind_at 或 notice 时刻）
    if tpl.kind == "notice":
        for m in members_of(tpl.role_ids):
            tgt = target_of(m.phone)
            if not tgt: mark_unactivated(m); continue
            send(tgt.user_id, render(tpl.text_tpl, m)); log_reminder(tpl, m)
        continue

    for m in members_of(tpl.role_ids):
        inst = ensure_instance(tpl, m, period_key(now))   # UNIQUE 保证不重复
        if inst.status in ("submitted", "approved"): continue
        tgt = target_of(m.phone)
        if not tgt: mark_unactivated(m); continue
        send(tgt.user_id, render(tpl.text_tpl, m, tpl.deadline))
        log_reminder(inst, tpl)

# 截止后 10 分钟扫一次，只发 1 次（靠 reminder_log 的 kind + 唯一性防重）
for inst in overdue_without_notice(now - 10min):
    send(inst.phone, "已逾期，72 小时内可补交：" + h5_link(inst))
```

### 5.3 幂等

```
idem_key = sha1(template_id | phone | period_key | kind | seq)
```
`seq` 区分：1 = 未完成提醒，2 = 逾期提醒，3 = 驳回重交提醒。

## 6. 平台通道技术结论（已实测，⛔ 不要重新试）

> 这些结论是花一整天试出来的。**新会话请直接采信，不要重复踩。**

### 6.1 取 token

```
POST https://imtwo.zdxlz.com/open-apis/v1/auth/token      ← 注意不是 /seal/oauth2/token
Content-Type: application/x-www-form-urlencoded
grant_type=client_credentials&client_id=<APPID>&client_secret=<SECRET>
→ 200 {"access_token": "...", ...}      有效期 7199 秒，缓存并提前刷新
```

⚠️ `/seal/oauth2/token` 签发的是 JWT，`/open-apis/*` **一律 401**，两套体系别混。

### 6.2 发单聊

```
POST https://imtwo.zdxlz.com/open-apis/v1/messages/v1/send
Authorization: Bearer <access_token>
X-Client-Id: <APPID>                        ← 必需，缺了照样 500
Content-Type: application/json; charset=utf-8

{"receive_id":"<平台 userId，19 位数字>","msg_type":"text",
 "content":"{\"content\":\"正文\"}", "idem_key":"..."}
→ 200 {"success":true,"code":200,"message":"SUCCESS"}
```

**500 的真实原因（已定论）**：机器人与该用户之间**没有会话**。参数怎么改都 500（连 `receive_id="abc"`、缺 `content` 都是 500）。用户先发一句话 → 会话建立 → 立刻 200。
**所以「未激活 = 发不出去」是平台机制，不是 bug，不能绕过。**

### 6.3 事件订阅（HTTP 模式，已在线上跑通）

```
POST http://<域名>:<端口>/api/app-events
Header: X-CTQ-Timestamp(毫秒) / X-CTQ-Nonce / X-CTQ-Signature(64 hex)
Body:   纯 base64 密文字符串（不是文档写的 {"data": ...} 包裹）
```

验签与解密（**照抄 `app/web/app_crypto.py`**）：

```
signature = HMAC-SHA256(token, timestamp + nonce + data)        # hex
key       = SHA256(encrypt_key + ":" + timestamp + ":" + nonce)  # 32 字节
iv        = base64decode(data)[:16]
plain     = AES-256-CBC(unpad) → JSON
```

**关键坑**：`encrypt_key` 必须用**后台那个字符串原样**参与运算。⚠️ 先做 base64 解码反而解不开（我在这上面浪费了两轮）。

事件体关键字段（真实样例）：

```json
{"appId":63474,"loginId":"<APPID>","eventType":"callback:direct",
 "userId":"3000000000000000001","groupId":"","toUserId":"8602191574774345334",
 "msgUid":"...","content":{"content":"你好"}}
```
- `loginId` **就是 AppID**（所以 `X-Client-Id` 填 AppID 是对的）
- `userId` 是**发送人**=我们要存的 `external_id`
- `toUserId` 是机器人自己的 ID，别拿它当收件人

### 6.4 未验证项（新会话必须补测，别当成已完成）

| 项 | 状态 |
|---|---|
| 平台侧发**图片/文件** | 🟡 **上传已验通**（`files/upload/init` → `PUT uploadUrl`（不带 Authorization）→ `/complete` 拿 `fileKey`），真实发图仍待会话。⚠️ H5 上传是传到**我们自己的服务器**，**和平台发文件是两件事** |

## 8. P0 范围与验收

### 范围（做这一批就够用）

1. 模板 CRUD（表单/图片/附件三类 + 是否审核 + 时点/截止/周期）
2. 角色 CRUD + 成员加人（单个 / 部门批量）
3. 激活：收事件 → 写 `delivery_target` → 后台显示「未激活 N 人」
4. 定时调度：未完成提醒 + 逾期提醒 + notice
5. H5：动态表单 / 图片上传 / 附件上传 / 提交
6. 后台：实例列表（谁交没交）、单条详情、代补交、简单完成率

### 验收（逐条可勾，缺一条不算完）

| # | 判据 |
|---|---|
| 1 | 到点准时发（误差 ≤1 分钟） |
| 2 | 已交的人不再收到催办 |
| 3 | 同一模板被两个角色关联，只发一条（实例唯一） |
| 4 | 未激活的人不发、后台可见并可导出 |
| 5 | 提交后状态正确（免审→`approved`，需审→`submitted`） |
| 6 | 截止后 10 分钟发 1 次逾期通知，第 2 次扫描不重发 |
| 7 | 超过 72h 置 `expired` 且拒绝补交（用户与后台都拒） |
| 8 | 重启服务不重发（幂等键 + `reminder_log`） |

### 11.1 提交类型的落列

§4 的 `task_template.kind` 只有 `form|notice`（区分「任务 / 待办通知」），
而 §3.1#1 的「表单 / 图片 / 附件三选一」是**另一个维度** → 加列：

```
task_template.submit_kind  [form|image|file]    -- notice 时为 NULL
```

### 11.2 时刻格式（`remind_at` / `deadline`）

```
"HH:MM"      日周期（周/月周期等价于 "1 HH:MM"）
"D HH:MM"    周：D=1..7（周一..周日）；月：D=1..31，超出月末自动夹到月末
```

§3.2#7 的 `remind_at < deadline` **按同一周期键解析成绝对时刻后比较**，⛔ 不比字符串
（否则 `"9:00"` vs `"18:00"` 这种会判错）。

### 11.3 激活绑定（§5.1③ 只说「系统自动」，平台事件只给 userId 不给手机号）

两条自动路径，**都要求手机号已在 member 名单内**，⛔ 不猜、⛔ 不人工后台填 userId：

| 路径 | 触发 | 流程 |
|---|---|---|
| a（主） | 未绑定用户给机器人发任意消息 | 回一次性链接（链接内含 userId，30 分钟有效）→ H5 填手机号 → 写 `delivery_target` |
| b（省事） | 用户直接发 11 位手机号 | 命中名单即绑定，回执「已绑定」 |

约束：**一个 `external_id` 只绑一个手机号，一个手机号只绑一个 `external_id`**（重绑会解绑旧的）。

### 11.4 时间边界

| 项 | 落地 |
|---|---|
| 补交硬边界 | `deadline + 72h`，**等于边界即 `expired`**（严格，§3.3#11） |
| 驳回重交 | 写 `task_instance.allow_until = max(原截止+72h, 审核时刻+24h)`（§3.3#13 保底） |
| 逾期提醒 | `deadline + 10min` 起扫，靠 `reminder_log.idem_key` 唯一索引防重 |

### 11.5 漏发补偿窗口

服务停机后重启，**只在** `[planned_at, planned_at + IMT_CATCHUP_MINUTES]`（默认 720 分钟）
内补发；超出即放弃该次提醒，⛔ 不做跨天补发（否则一次长时间停机会把历史周期全轰一遍）。

### 11.7 幂等的实现方式与代价

`reminder_log.idem_key` 唯一索引是**唯一**手段：先 `INSERT`（claim）再发，
冲突即「已发过」。代价：claim 成功但进程在发送前崩掉，**这一条不会再发**
（取舍：宁可漏一条，不可重复催 —— 对齐 §8#8）。

### 11.8 P0 明确没做（P1 范围，别当成漏了）

投递回执（`delivered` 状态）、驳回重交的推送、统计导出 Excel、平台侧发图片/文件、
多管理员分权、模板停用后的实例收尾。

### 11.9 后台界面

单个自包含 HTML（`src/imtask/static/admin.html`），**浅色 + 无构建工具 + 无 CDN**，
与群运维机器人后台的 Tabler 浅色基调一致（⛔ 未沿用 DUSK 黑金，那是小程序/封面风格）。
（⚠️ 2026-10-26 起后台界面规划改为「等 AI Studio 原型出来后一比一复刻」，本页仅作 P0 期间可用实现。）

### 11.10 双端口与端口规划（2026-10-26 用户指令）

用户要求先把两个端口**占位并报给运维配防火墙**，同时保证后台未就绪时核心功能照常启动。

| 用途 | 监听 | 暴露范围 | 提供路径 |
|---|---|---|---|
| **业务端口（平台回调 + H5）** | `0.0.0.0:9012` | **需公网可达** | `POST /api/app-events`、`GET /h5/task`、`GET /h5/activate`、`POST /api/h5/*`、`GET /healthz` |
| **管理后台** | `0.0.0.0:9013` | 内网 / 运维（可放开） | `GET /`（根路径即后台单页）、`/login` `/instances` 等前端路由、`/api/admin/*`、`GET /healthz` |

> **2026-10-27 端口定案**：紫玉分配 **9012 / 9013**，原 `18090 / 18091` 作废。
> 主线 `app/` 的环境变量是 `IMT_PUBLIC_PORT` / `IMT_ADMIN_PORT`（旧 `src/imtask` 用 `IMT_BOT_PORT / IMT_ADMIN_PORT`，勿混）。
> ⚠️ 后台入口是**根路径 `/`**，`/admin` 在主线里不存在（实测 404）。
> 实测：9013 `/` 200（48,861 字节）、`/api/admin/me` 401；9012 `/` 404、`/h5/task` 200。

九条约束：

1. 两个端口是**同一进程的两个监听**，共用同一份 `store / service / scheduler`（数据只有一份）。
2. 路由**硬隔离**：业务端口不挂 `/api/admin/*`（实测 404），后台端口不挂 `/h5/*` 与 `/api/app-events`。
3. 任一端口起不来**不影响另一个**：后台没就绪时，机器人照样收回调、发提醒。
4. 调度器只在启动器里起**一次**，不随端口重复启动。
5. **两个端口都绑 `0.0.0.0`**（2026-10-26 用户要求后台也对所有人开放，原来后台只绑本机）；
   后台当前只有「单账号密码 + HTTP 明文」一层保护 → 上线前必须改默认密码，后续套 HTTPS 反代。
6. 回调地址 = `http://<公网地址>:9012/api/app-events`；由 `IMT_PUBLIC_BASE_URL` 决定，仍是 `127.0.0.1` 时服务会打 WARNING。
7. H5 链接前缀同源，取 `IMT_PUBLIC_BASE_URL`。
8. 出站需放行 `imtwo.zdxlz.com:443`（取 token / 发单聊 / 上传文件）。
9. 端口由 `IMT_PUBLIC_PORT / IMT_ADMIN_PORT` 决定；**任何改动都要同步通知运维与我**，否则防火墙白配。

自检命令：`python -m imtask --plan`（看规划）/ `python -m imtask --check`（试绑端口）。
接口契约快照：`docs/api-openapi-20261026.json`（bot 9 条路径 / admin 21 条路径），后台原型按 admin 部分对接。

### 11.11 部署环境与凭据现状（2026-10-26 实测）

| 项 | 状态 | 说明 |
|---|---|---|
| 平台 `APP_ID` / `APP_SECRET` | ✅ 已配、**实测可用** | `POST /open-apis/v1/auth/token` 返回 access_token（493 字符，JWT 形态），端点与 §6.1 一致 |
| `ENCRYPT_KEY` / `VERIFY_TOKEN` | ❌ 未拿到 | 缺这两项事件回调一律 401，**事件进不来**，属当前唯一阻塞项 |
| 服务器 | ⏳ 待定 | 运维（吴波）答复：`203.0.113.10`（天翼云测试机）**内存不够，不要再往这台部署新项目**，「本地有测试服务器」 |
| `IMT_PUBLIC_HOST` | ⏳ 待定 | 回调地址与 H5 链接依赖它，换服务器就要跟着改 |
| 应用可见范围 | ✅ 不卡 | 业务方本人持有权限，可随时调整（见 §3.5#21） |

**⚠️ 部署前必须先答清的一条**：平台回调是**平台主动访问我们**，所以机器人服务所在机器**必须能被平台从公网访问到**。
如果最终落在「本地测试服务器」（内网机），则要么有公网映射 / 反向代理，要么把 `203.0.113.10` 当跳板反代到内网。
这条不确认，服务部署上去也是收不到事件的。

**防火墙申请时机**：⛔ 不要在服务器未定、代码未部署时就提交。
放行规则是绑「某台机器 + 它的安全组」的，机器没定、端口上没有服务，报上去也验不了。
正确顺序：定机 → 部署 → `--check` 自测 → 提交放行 → 平台填回调点测试 → 联调。
